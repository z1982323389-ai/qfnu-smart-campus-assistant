# 第三阶段完成说明

## 当前目标

第三阶段目标是把第二阶段的工程骨架升级为适合比赛演示的 UI 原型。此阶段仍不接入真实 Coze API，也不实现知识库检索，重点是让产品定位、核心链路和可维护能力在界面中清晰呈现。

## 为什么这样设计

比赛评委需要在很短时间内判断项目是否真实、有用、可落地。单纯的页面骨架无法证明产品价值，因此本阶段围绕“不是聊天机器人，而是校园办事平台”重构页面表达，让首页、聊天页、办事大厅、知识库和后台共同讲清楚产品闭环。

## 完成内容

- 新增统一校园服务数据源 `config/campus.ts`，集中维护八个首版模块、示例问题、答案结构、标签和来源类型。
- 首页新增首版模块预览、AI Workflow 链路、可信边界、资料可追溯和可部署价值说明。
- AI 聊天页升级为结构化咨询答案原型，展示核验步骤、材料提示、咨询渠道、来源状态、边界提醒和推荐问题。
- 校园办事大厅改为模块卡片和回答结构预览。
- 热门办事页补充演示价值说明，明确现场优先演示“学生证补办”“奖学金申请”“通知解读”。
- 知识库页补充知识条目示例、版本状态、标签和可信回答规则。
- 后台配置页补充知识库管理预览，展示分类、来源、启用状态和更新时间。
- 新增可复用组件 `WorkflowPreview` 和 `ServiceModuleCard`。

## 自查结果

- 页面范围与第一阶段 PRD 保持一致，没有新增依赖内部系统的功能。
- AI 聊天页明确标注为演示原型，没有伪装成已接入真实 AI。
- 涉及个人数据查询的能力仍然未实现，产品边界清晰。
- 已修复首页图标数组和后台模块数组的 TypeScript 推断隐患。
- 依赖安装仍受 npm 网络状态影响，需在网络可用时执行安装和构建验证。

## 下一阶段计划

第四阶段将进入 AI 与 API 基础层开发。目标是先建立服务端 AI 调用封装、统一 API 响应结构、Zod 参数校验、错误处理、重试和限流骨架。真实知识库检索可在第五阶段接入，避免 AI 接口与知识库同时开发造成调试复杂度过高。
